# AUTH base64 runs on base64-codec

The base64 crate gave way to base64-codec 0.1, as the family decided on 2026-11-03. src/rfc4954/auth.rs and src/rfc4954/auth_data.rs encode through `encode_vec` straight into the command buffer, which also drops the intermediate String that held each credential's base64, and decode through `decode_vec`, refusing what did not read clean. `SmtpAuthDataError::Base64` and `SmtpAuthChallengeError::Base64` lost their string payload. **Breaking.**

The lenient decoder skips blanks, which broke the SCRAM success path: it took any 235 text that decoded as the server-final-message, and `Authentication successful` had only been safe because the strict decoder refused its space. The path now takes one blank-free token decoding to `v=` or `e=`. That also fixes a bug the strict decoder had: a one-word text such as `Accepted` decoded, reached the mechanism after a verified exchange and failed it with `UnexpectedChallenge`; the extended `success_with_server_final_in_a_challenge_returns_ok` fails that way against the previous commit. The LOGIN test feeding `not base64 at all` now feeds `not!base64`, since the blanks are skipped.

io-sasl moved to base64-codec the same day (io-sasl 608192d), unreleased: until it is published and the lockfile updated, the default `scram` build still pulls base64 0.23 through it.

The redundant `coroutine::*` imports the current toolchain flags in 18 test modules are gone.

Capabilities moved: auth (ADDED "AUTH payloads decode leniently").

Verified: `cargo clippy --all-targets --all-features` clean, `cargo test --all-features` 108 unit tests and 36 + 7 + 19 integration tests passed, clippy clean on `--no-default-features` alone and with `scram`, `client` and `rustls-ring`, rustdoc with broken intra-doc links denied.
